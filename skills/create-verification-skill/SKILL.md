# Create a verification skill

Every serious project needs a scripted way to drive the real app and prove behavior: launch it, exercise a feature the way a user would, and capture evidence. This skill generates that as a project-local skill (`.claude/skills/verify-<app>/`) tailored to the repo. It has two parts. The **feature map** tells the agent where each feature lives and how to reach it, so it reads one file instead of searching the codebase. The **driver CLI** (`scripts/<app>-cli.mjs`) is the only way the agent touches the app: `<app>-cli open /notes`, `click button:Save`, `snapshot` for pages, `<app>-cli http POST /api/notes --json '{"title":"x"}' --expect 201` for an API. Waits, auth, seed, and flake handling live once inside the CLI, so they get tested and reused instead of rewritten every session. The **verify-web** skill drives every browser and HTTP criterion through it. You write the generator's output for the next agent, not for a human: it will be read cold, mid-task, by an agent that has never seen the app.

## 1. Interview the repo, not the user

Answer these from the codebase and only ask the user what you cannot observe:

- **Surface:** what does a user actually touch? Pages and routes in a browser, a JSON API, server-rendered forms, webhooks? Record it as one word: `ui` (pages only), `api` (HTTP only, no pages), or `both`. Server-rendered forms are `ui`. A webhook receiver is `api`. Every later step reads this word.
- **Run:** how does the app start locally? Prefer the repo's own documented dev command (package scripts, Makefile, README quickstart). `node <plugin root>/scripts/config.ts get devServer` may already hold the command and base port, and the "Dev-server & verification recipe" of each active **pack-<p>** skill (`node <plugin root>/scripts/detect.ts`) gives the port flag, the ready path, and how the server forks. The CLI kills the whole process group it started, so forked children go with it. Note the port and how to set it, env vars, migrations, seed data, and auth.
- **Auth kind:** pick one from the code. `none`: no sign-in, so `auth` is `null`. `form`: a login page, so `auth` is the browser form (`route`, `steps`), and it needs Playwright. `http`: a login route that sets a session cookie, so `auth` is `{ "http": { "method", "route", "json" } }`, with no Playwright. `token`: a bearer token or API key, so `auth` is `null` and every request carries `--header "Authorization: Bearer {env:VERIFY_TOKEN}"`. An `api` surface with a cookie session is `http`, never `form`. Name the env vars the fixture credentials come from (`VERIFY_USER`, `VERIFY_PASS`, `VERIFY_TOKEN`) and where the seed gets them.
- **Drive:** `<app>-cli http` needs nothing beyond Node. The browser commands need the project's own Playwright (`playwright` or `@playwright/test` in `package.json`). For an `api` surface, skip Playwright entirely: never ask, never install. For `ui` or `both` with Playwright missing, ask the user once with `AskUserQuestion` whether to add it as a dev dependency (`npm i -D playwright && npx playwright install chromium`, with the repo's package manager). Inside a delegate (a brief that says to read `worker.md`, or a headless run without `AskUserQuestion`), never ask: generate without it and put the install command in your report as a proposal. A no, or no answer, means browser criteria stay INCONCLUSIVE; say so and generate the HTTP parts only. Reuse what exists: Playwright specs for selectors, a seed or fixture script, a test-user factory.
- **Observe:** what evidence can be captured? Screenshots, ARIA snapshots, Playwright traces, console errors, response bodies, server logs, DB rows. An `api` surface proves with `http --out` files and a second read, never a screenshot.
- **Handles:** for an `api` surface, the handles are the contract: method, route, request fields, response shape, status codes. Read them from the route handlers and validators. There is no marker; set `rootMarker` to `null`. For `ui` and `both`, find the stable handles the CLI will target: ARIA roles and accessible names, `data-testid`, labels. Pick one **app root marker** that every app page renders, so the CLI can tell the app apart from an error page or a login redirect. Prefer what already exists and is stable: a landmark (`main`), a heading, an existing `data-*` attribute, route-specific text. **Never edit product code to get a marker.** Only when no stable marker exists may you propose a test handle (for example `data-testid="app-root"`), and only as a proposal: list it in your final report under "Proposed product-code changes (not applied)" with the file, the line, and why nothing existing works. Do not apply it. Until the user accepts it, the generated skill must not depend on it; set `rootMarker` to the best existing handle or leave the marker check to the weakest existing one, and say so.
- **Isolate:** can two instances run side by side (ports, databases, data dirs)? Resonator gives each worktree its own port. Say in the generated skill whether the database is shared and what that means for seed data: refusing to double-drive a shared instance beats corrupting the user's session.

If the checkout doesn't build or start as-is, fix that first (or report it precisely) before generating; a skill written against a broken base teaches wrong steps. When an irrelevant missing asset blocks startup (a static dir the API never serves, a sample config), the generated skill may create it, clearly marked as verification scaffolding, and remove it in cleanup.

## 2. Generate the skill

**Ship the CLI.** Copy `<plugin root>/skills/create-verification-skill/templates/app-cli.mjs` (`<plugin root>` is two levels above this skill's folder) to `.claude/skills/verify-<app>/scripts/<app>-cli.mjs` and `chmod +x` it. Write only under `.claude/skills/verify-<app>/` (and `.git/info/exclude`). If a write there is refused (a headless `claude -p` run can refuse writes under `.claude/`), do not retry another way and never stage in `/tmp`. Write the whole skill folder under `.resonator/verify/staged/verify-<app>/` instead, run the proof from there if the paths allow, and end the report with the exact command for the user: `mkdir -p .claude/skills && cp -R .resonator/verify/staged/verify-<app> .claude/skills/`. Fill the `resonator-config` block at the top with what the interview found: `app`, `port`, `baseUrl` (`{port}` is substituted), `launch` and optional `teardown` commands, `readyPath` (a route that answers only when the app is usable), `rootMarker`, `seed.command` and a read-only `seed.check`, the `auth` fixture, and `flag`. A `form` auth is `route`, `steps` as `["fill"|"click"|"press", target, text]`, and a `check` route that is 2xx only when signed in. An `http` auth is `{ "http": { "method": "POST", "route": "/api/login", "json": { "email": "{env:VERIFY_USER}", "password": "{env:VERIFY_PASS}" } }, "check": "/api/me" }`: `login` sends that one request and stores its Set-Cookie in the jar. Credentials are always `{env:NAME}`, never literals in the file. The CLI expands `{env:}` from `process.env` only, and only in `auth.http.json` and `--header` values. A missing variable exits 2 with its name. Set `"auth": null` when the app has no sign-in: `login` then prints `skip no auth` and exits 0, and `doctor` has no `auth` line. Set `"rootMarker": null` when the app has no pages: the marker check is skipped. `{port}` and `{baseUrl}` are substituted in `launch`, `teardown`, and both `seed` commands, and `doctor` prints the substituted `seed.check`. Fill `flag` (`cookie` or `localStorage`, plus a key prefix). The CLI refuses to run while any `<fill` placeholder remains. Adapt the code only where the app needs it (a flag API instead of a cookie, an OAuth stub), and keep every change inside the CLI. Add `.resonator/` to `.git/info/exclude` if it is not ignored.

Write `.claude/skills/verify-<app>/SKILL.md` with YAML frontmatter (`name: verify-<app>` and a `description` that names the app, the surface, and when to reach for it; without frontmatter the skill never registers) and these sections, each grounded in what the interview actually found (no placeholders left). The first line under the H1 is `Surface: ui`, `Surface: api`, or `Surface: both`; **verify-web** and **maintain-verification-skill** read it. Every section is CLI calls. Leave out what the surface does not use: an `api` skill has no `start`, `open`, `snapshot`, or `screenshot` anywhere in it. Write `cli` below as the real path, `node .claude/skills/verify-<app>/scripts/<app>-cli.mjs`.

- **Launch:** `cli launch --port <port>` starts the app, waits until `readyPath` answers, and records the PID. `cli seed` loads the fixture. For `ui` and `both`, `cli start` opens the long-lived headless browser (`--headed` to watch); action commands also start it on demand. Launch must reach a usable state from an empty database, including migrations and seed data. Ready means usable, not just that a process answers. A database health check can pass while its init scripts are still running.
- **Auth fixture:** for `form`, `cli login` signs in as the seeded user through the real login form and saves the session to `.resonator/verify/state.json`, plus a cookie jar at `.resonator/verify/cookies.txt`. For `http`, `cli login` sends the configured request and writes only the jar. Either way `cli http` sends the jar on every request, and `curl -sS -i -b .resonator/verify/cookies.txt ...` can use it too. For `token`, say which env var holds the token and show the `--header "Authorization: Bearer {env:VERIFY_TOKEN}"` form. Name the env vars the credentials come from. Name the account and say it is a fixture. Never use a real person's account. With `auth: null`, say the app has no sign-in and that `cli login` prints `skip no auth`.
- **Doctor:** `cli doctor` answers "is this instance worth driving?": process up, port owned by our PID, ready, seed present, auth valid. It exits non-zero with the reason. Run it first, and again whenever anything looks off.
- **Drive:** for `api` and `both`, one request per call: `cli http <METHOD> <route> [--json <body>|--json-file <path>] [--header k:v]... [--expect <status>] [--out <path>] [--save-cookies] [--timeout <ms>]`. It prints `<status> <body>` on one line, truncated, refuses any origin but the app, and exits 1 when the status does not match `--expect` (`201`, `2xx`, or `200,204`). `--save-cookies` merges the response's Set-Cookie into the jar. A bad header or `--timeout` exits 2. `--json` is sent unchecked, so a malformed body can be proven too. For `ui` and `both`, one structural action per call, with a fresh `cli snapshot` before and after it: `cli open <route>`, `cli click <target>`, `cli fill <target> <text>`, `cli press <key>`, `cli wait --text <t>|--testid <id>|--idle`, `cli reload`, `cli flag <name> on|off`. Targets are `role:name` (`button:Save`), `testid:<id>`, `label:<text>`, or `text:<text>`, tried in that order. Never coordinates, never CSS chains. Every action waits for the page to settle, and on failure prints the URL and a snapshot excerpt. `cli open` fails when the app root marker is missing. `cli status` prints the app and browser PIDs as JSON.
- **Evidence:** for `api` and `both`, `cli http ... --out <path>.json` writes the request, status, headers, and body as JSON. Cookie values, Set-Cookie values, and `{env:}` secrets are never recorded. For `ui` and `both`, `cli screenshot --out <path>`, `cli snapshot --out <path>`, `cli trace start` then `cli trace stop --out <path>.zip`, and `cli console` (console and page errors since the last call). Default to `.resonator/evidence/<branch>/`, the folder **verify-web** uses. State the proof standards: exercise the real user path, not internal setters or test-only endpoints; capture the action and the resulting state, not just the final screen; verify side effects (rows inserted, emails queued, files uploaded) alongside what's visible; mocks only where a production boundary already isolates the external system. When the safe path is a dry-run or test mode, verify what it actually skips by observing (network calls, rows, outbound mail) rather than trusting its name.
- **Cleanup:** `cli cleanup` stops the browser if one runs, kills the app's process group by its recorded PID (never by process name), runs `teardown`, and keeps the evidence. Name what seed data the run leaves and how to reset it.
- **Helpers:** list every command that applies to the surface, with one real invocation each. Every surface: `launch`, `doctor`, `seed`, `login`, `cleanup`, `status`. `login` runs on an `api` surface too: an `http` auth needs no browser, and `auth: null` prints `skip no auth`. `api` adds `http`, with a `--save-cookies` example when a route other than login sets a cookie, and the `--header "Authorization: Bearer {env:VERIFY_TOKEN}"` form for a `token` auth. `ui` adds `start`, `stop`, `open`, `click`, `fill`, `press`, `snapshot`, `screenshot`, `trace`, `console`, `wait`, `reload`, `flag`. `both` lists them all. Never list a command that cannot run here, not even as "exits 3". A helper the reader has to reverse-engineer is not a helper. A missing command is a CLI change, not an inline script.

## 3. Seed the feature map

Create `.claude/skills/verify-<app>/features/README.md` plus one file per user-facing feature you can identify (aim for the top 3-5 to start, from routes, API handlers, navigation, or docs). Follow the shape in [`references/feature-map-example/`](references/feature-map-example/), with a README index and one file per feature. Each file answers, from the user's point of view: what the feature is, how to reach it, how to drive it with the CLI, and what observable end state proves it works. Under the H1, a header block names `Route:`, `Selectors:` (the stable role and testid handles) for a UI feature or `Contract:` (method and route, request fields, response shape, status codes) for an API feature, `Preconditions:`, `Expected:` (the observable end state), and `Ownership:` (the source files: the entry point and the state owner), so the agent opens those files instead of searching. The four H2s are `Sub-features`, `How to get to it (user POV)`, `Driving it with <app>-cli`, and `Gotchas`. The driving section is a list of CLI calls with the result each one should show, not code. An API recipe is `cli http` calls with `--expect`, never curl. If the seed data lacks a precondition that a journey needs, the journey reports a failure and the reason goes in that feature's `Gotchas`. Never weaken the journey to make it pass. The map is the repo's maintained verification source; a proof that drives one convenient entry point is incomplete when the map lists others.

## 4. Prove the generated skill before handing it over

Run its own instructions end to end once, through the CLI only, along the surface you recorded. Drive ONE mapped feature (one is enough; the map exists so later runs can cover the rest).

- `ui`: `launch`, `seed`, `login`, `doctor`, drive the feature, capture a screenshot, a snapshot, and `console`, then `cleanup`.
- `api`: `launch`, `seed`, `login` (an `http` auth, no browser), `doctor`, then `http` for the feature with `--expect` and `--out`, plus a second `http` read that shows a mutation stored, then `cleanup`. No screenshot, no snapshot.
- `both`: the `ui` proof and the `api` proof in one session, before one `cleanup`.

Skip `login` whenever `auth` is `null`; the proof is then `launch`, `seed`, `doctor`, and the drive. After cleanup, confirm the evidence still exists at the named location and that `cli status` shows nothing alive. A cleanup that eats the proof fails this step. Fix what fails in the CLI or the config block, and run `cli cleanup` after every failed iteration too, so broken attempts don't strand processes and ports. A generated skill that was never executed is a draft, not a deliverable. If you proved it in a stand-in for the real target (a local database in place of a staging one, a mocked mail server in place of a real one), list every setup step the stand-in did that the target will not. Those steps stay unverified until a run on the real target covers them.

## 5. Offer the maintenance loop

Point the user at `/resonator:maintain-verification-skill` for keeping the map and the CLI honest as the app changes. It is meant to run daily against a local app; `/resonator:setup-resonator` offers the schedule. Suggest a cadence only if they ask.
