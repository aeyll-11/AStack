# Maintain a verification skill

A feature map rots the moment the app changes, and so does the driver CLI that walks it. This skill is the upkeep loop for a skill generated by `/astack:create-verification-skill` (or any project-local verification skill with a feature map). It is built to run daily against a local app. The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet. `<plugin root>` is two levels above this skill's folder.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed**: one PR ships proven doc, harness, or map corrections.
- **blocked**: coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, features/, and its `scripts/<app>-cli.mjs`, config block included). If a write under `.claude/skills/` is refused (a headless `claude -p` run can refuse writes under `.claude/`), do not retry another way and never stage in `/tmp`: write the corrected files under `.astack/verify/staged/<skill>/` mirroring the skill's layout, report `blocked` or `changed` with that staging path, and give the user the exact copy command, `cp -R .astack/verify/staged/<skill>/. .claude/skills/<skill>/`. Never edit product code during a run, and never add test handles or markers to it: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs). A missing stable marker or handle is not an edit: switch the map to an existing handle (landmark, heading, existing `data-*`, route text), or list a proposed test handle in the report (file, line, why) without applying it, and keep the skill independent of it until the user accepts.

## Pass

0. **Locate the target.** An argument naming a skill (`/astack:maintain-verification-skill verify-<app>`) picks `.claude/skills/<name>/`; use it and never ask. If it does not exist, the outcome is `blocked`. With no argument, find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (usually `.claude/skills/verify-*/`). Several candidates → ask which one with `AskUserQuestion`, or, when `AskUserQuestion` is unavailable (a headless `claude -p` run), report `blocked` with the candidate names instead of asking; none → stop and point at `/astack:create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight; no generated inventory.

2. **Source wave.** One read-only agent per feature file, launched concurrently in one message. Use the `Agent` tool with `subagent_type: "Explore"` and put "do not edit files" in each brief. Run `node <plugin root>/scripts/config.ts model verify` and pass the printed `model` and `effort`. Each explains "how does this user-facing feature work?" from source (routes, page components, API handlers, middleware), starting at the feature's `Ownership:` paths. It checks that each `Ownership:` path still exists and still owns the entry or the state, and that each handle under `Selectors:` still appears in the source with that role, accessible name, label, or `data-testid`. It flags likely doc drift with citations and returns one concise live-verification recipe as `<app>-cli` calls. Children never drive the app and never edit files. Return shape: feature summary / source entry points / Ownership and Selectors drift or none / other likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map (new routes, pages, API endpoints). Require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; drive only through the project's CLI (`node .claude/skills/verify-<app>/scripts/<app>-cli.mjs`): `launch`, `seed`, `login`, then `open`, `click`, `fill`, `press`, `wait`, with a `snapshot` before and after each action, and `screenshot`, `console`, and `trace` for evidence. One long-lived dev server and one signed-in browser session, driven serially. Never write a one-off browser script; a step the CLI cannot do is a harness gap. Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising: `<app>-cli doctor` before the first drive, again after any failed drive, and where doctor can't see the failure (a wedged page state on a healthy server, an expired session), `reload`, `login` again, or `cleanup` and relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness; `<app>-cli status` shows what is alive. Failed-iteration residue (stray rows, uploaded files, browser contexts, servers) is cleaned whether the drive is stuck, exited, or shared. For a shared instance, clean the residue, not the instance. A doctor failure caused by skill drift is drift: fix it under edit scope and retry once, restarting only what the fix invalidated, before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth role, feature flag, paid plan, external service) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it ships. Final teardown is `<app>-cli cleanup` after the last drive of the run, including those re-proofs, so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the CLI can't drive (a flaky wait, a missing command, a stale config value) → harness gap, fix it in `<app>-cli.mjs` and re-drive the feature live through the fixed CLI; a harness fix follows the same helpers rule as generation (script executable, every command's invocation documented in the skill body). Wrong `Ownership:` paths or `Selectors:` handles are doc drift. App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Ship or stop.** For changed: one PR of proven corrections through the **opening-a-pr** playbook (`<plugin root>/skills/astack/playbooks/opening-a-pr.md`). Re-read every changed file first. For clean or blocked: no PR, report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
